## 查实问题

### F24-1 / P2：保留尾音后，疼痛弹窗或暂停不能取消实际语音

改动位置：[voice_queue.dart:190–191](https://github.com/mhgd3250905/HipLab/blob/e3655e50e2ff7868d9d381489df90efe9cf208f1/lib/hip/voice/voice_queue.dart#L190-L191)。新增 tailGrace 允许上一句保留最多 0.8 秒尾音，却立即 `_start` 下一句，并用请求时刻加新句时长覆盖 `_current.end`（209–215）。新控制器实际顺序播放，真实结束晚于此预测；`cancelAll`（228–231）仍只在预测 `_busy(now)` 时停止输出，因而可能既不停止旧句，也不作废后端已排队的倒数。

独立专项使用真实 D 套路、英文 manifest、SessionEngine → Queue → LineController，平台加载/调用延迟均为零：先中断并恢复，将恢复语音尾部与 n.5 相交；active **50.65** 秒打开疼痛弹窗并冻结训练时钟。实际仍在播放 `p.resume`，取消后还开始 `n.5`，`stopped=[]`。另一个 600ms 加载专项按播放器手动暂停的 `cancelAll → p.paused` 顺序，也观察到旧 info 播到 3.6 秒、旧 n.3 在 4.2–4.664 秒继续播放。

控制组只换回目标 main 的 Queue/LineController，共用当前模型与同一 Engine 事件；相同疼痛测试通过，恢复句被立即停止，取消后无倒数。该对照隔离本 PR 的队列/控制器改动，不冒称完整 main APK 对照。

最小修复方向：取消必须无条件通知输出停止并作废排队语音；不能再以名义 `_busy` 判断实际声音是否存在。保留“尾音保护 → 暂停/疼痛 → 后端无遗留句”回归。

### F24-2 / P2：异步设置音量时缓存了另一数值，后续调低音量失效

改动位置：[voice_line_controller.dart:177–179](https://github.com/mhgd3250905/HipLab/blob/e3655e50e2ff7868d9d381489df90efe9cf208f1/lib/hip/voice/voice_line_controller.dart#L177-L179)。调用 `await p.setVoiceVolume(volume)` 后，`_lastVolume = volume` 重新读取可变字段。若这次平台调用尚未返回时用户将 1.0 改为 0.25 并再次试听，平台本次实际应用 1.0，缓存却记录 0.25；以后请求的 0.25 均被误认为已应用，继续以旧音量播放。

入口可达：进度页音量滑块和可重复点击的试听（`hip_app.dart:1423–1450`）通过 `HipVoice.queue()` 设置共享 output/controller 的 volume。受控平台 Future 专项观察 `appliedVolumes=[1.0]`，正确期望为 `[1.0, 0.25]`，测试失败。换 main 控制器的对照通过音量断言；对照不要求旧控制器保留其本来会被后续请求取代的第一句。

修复方向：调用前捕获本次目标值，平台参数和成功后的缓存写入使用同一个局部值；补异步调用期间改变设置的回归。

### F24-3 / P2：自然完成后仍持有 CPU 唤醒锁和前台服务

改动位置：[screen_awake.dart:40](https://github.com/mhgd3250905/HipLab/blob/e3655e50e2ff7868d9d381489df90efe9cf208f1/lib/core/platform/screen_awake.dart#L40)。新增 Android 服务直接跟随旧的“页面打开”引用计数，而非“训练仍在运行”：播放器在初始化 acquire，只在 dispose release；`_complete`（hip_player_page.dart:169–173）、神经疼停止（315–320）以及自测进入结果（hip_assessment_page.dart:369）均不会释放。

因此锁屏/后台中训练自然结束，用户不返回点击回首页时，语音与计时已经结束，服务仍保留“训练进行中”状态。`PARTIAL_WAKE_LOCK` 最久继续到开页后 3 小时，服务自身没有完成时限；原有屏幕常亮生命周期不能替代新 CPU 保活生命周期。这是源码查实，未声称已采到真机耗电量。[Android 定时唤醒锁规则](https://developer.android.com/reference/android/os/PowerManager.WakeLock#acquire(long))。

修复方向：终态按实际活动任务释放服务 hold，安全处理收尾音频；若支持再次开始则重新获取。覆盖正常完成、自测结果、神经疼停止及重开，避免和 dispose 双重释放。

### F24-4 / P2：旧 STOP 请求可能终止已经重新开始的服务

改动位置：[TrainingSessionService.kt:80–83](https://github.com/mhgd3250905/HipLab/blob/e3655e50e2ff7868d9d381489df90efe9cf208f1/android/app/src/main/kotlin/com/ugk/hiplab/TrainingSessionService.kt#L80-L83)。`onStartCommand` 收到旧 ACTION_STOP 后调用 `finish()`，释放锁、移除前台状态并无条件 `stopSelf()`，完全忽略 startId；静态 running 标记在 start/stop 请求交付前就改变，不能区分请求代次。

触发条件：退出后快速重开，新的 START 已到系统，但旧 STOP 先在服务中处理、新 START 尚未交付。旧停止会关闭更新的服务生命周期；Dart 侧仍持有一个 hold，没有失败重试，后续后台训练失去保活。[Android 官方 stopSelfResult(startId) 说明](https://developer.android.com/reference/android/app/Service#stopSelfResult(int))明确覆盖“客户端新 start 尚未投递”的情形。本项是源码/API 规则查实，未声称已在设备复现时序或发生概率。

修复方向：用请求代次/最新期望状态裁决停止；不仅替换 stopSelf，还须防止旧请求提前释放新任务共用的锁和前台状态。覆盖 start → stop → start 的快速请求及真正最终 stop。
