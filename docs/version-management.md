# 版本管理说明

本页说明 HipLab 的版本与台账如何维护。共用版本取自 [`pubspec.yaml`](../pubspec.yaml)，逐次构建、安装和发布事实继续写入[版本交付台账](version-ledger.md)，本页不另建交付流水。核对日期：2026-10-20，北京时间。

## 事实来源

| 需要确认的事实 | 维护位置 | 记录要求 |
|---|---|---|
| App 共用版本 | [`pubspec.yaml`](../pubspec.yaml) 的 `version` | Windows 统一维护；Mac 不独立递增 |
| 当前主线、设备和完成边界 | [当前状态](current-state.md) | 写最后实际核验日期；区分 Git 与手机 |
| 每次 APK、安装、发布 | [版本交付台账](version-ledger.md) | 按日期追加身份和结果，保留旧记录 |
| 检查及未验范围 | [验证台账](verification.md) | 命令、结果、执行时间/来源、完整源码 SHA；沿用证据说明差异 |
| 未完成验收及后续事项 | [开发事项](development-roadmap.md) | 代码合入与真机验收分开关闭 |
| 决策和关键成果 | [开发日志](development-log.md) | 链接对应台账或专题证据 |
| 操作步骤与协作分工 | [开发工作流](development-workflow.md)、[AGENTS.md](../AGENTS.md) | Windows 主干线、Mac 分支 PR；保留既有改动和用户数据 |

根 [README](../README.md) 和[文档入口](README.md)只摘要并链接上述来源。旧日期的专题报告保留当时结论；有后续修复、合并或安装时追加新事实，当前摘要指向最新结果。

## 版本与来源身份

共用版本采用 `版本名+构建号`，例如当前 `0.3.7+12`。Android 此次实包回读为 versionName `0.3.7`、versionCode `12`。准备新版时由 Windows 在 `pubspec.yaml` 统一递增；检查新构建号高于此前交付包，保留包名和签名连续。iOS 共用版本的变动不代表已在 Mac 构建、安装或验收。

单独的文档整理、合并事实补记不递增 App 版本，也不触发重新构建或安装。审核期曾有多份相同 `0.3.6+11` 的包，不能只凭版本名判断内容；必须结合构建源码、APK SHA256、大小和签名识别。

构建源码 SHA、已验业务来源 SHA、PR 合并提交和后续文档 HEAD 可以不同，分别记录。复用早先测试时先比较到当前树的有限差异；只有业务、资源、原生代码、测试和锁文件未受影响，才能按原来源引用，不能写成新 HEAD 已重新执行。构建证据始终归属于实际构建源码；文档提交不会产生新 APK。

App 版本、`ugk_coach` SDK 版本和 Pose-Hub 素材版本分别维护。目前 SDK 为 `0.1.2` / `26e32557058e582d3f1b2b7f722dfa53c2b16aa6`，素材冻结 Pose-Hub `v0.2.0`；App 递增不自动升级依赖或素材，恢复步骤见[文档入口](README.md#新机器拉素材mac--windows)。

## 状态分别登记

| 状态 | 可以据以登记的事实 | 不据此推断的后续状态 |
|---|---|---|
| 已构建 | 固定源码构建成功，并核验实际包身份 | 手机安装、真机通过或商店发布 |
| 已安装 | 实际安装结果、设备/时间和包身份；用户反馈注明来源 | 新功能完整验收或其他设备通过 |
| 已验证 | 具体命令/场景及结果，绑定源码和环境 | 未执行的原生、iOS 或系统矩阵 |
| 已合并 | 来源/目标 SHA、实际集成结果及 PR 状态回读 | 手机已更新或商店已发布 |
| 已推送 | 普通 push 成功并回读远端分支 SHA | APK、日志、数据备份已上传 |
| 已发布 | 实际渠道回执、版本、时间与发布状态 | 仅构建或提交审核即正式上线 |

“待安装”“待验收”须保留。打包、合并、推送按各自实际完成情况更新，不互相代替；本机忽略目录中的产物路径也不代表已有远端备份。

## 每次交付如何对齐

1. 开始时读当前状态和事项台账，核对实际分支、完整工作区状态、固定源码和远端目标。使用 Flutter **3.44.7 stable / Dart 3.12.2**；不清理既有改动。
2. 业务改动按影响验证，必要时补原生证据；新版由 Windows 递增共用版本并固定构建源码。仅文档修改检查事实、链接和 `git diff --check` 即可，不重跑无关构建。
3. 构建后记录版本、完整源码 SHA、构建命令/时间、SDK、包名、架构/构建类型、文件名、字节数、SHA256和签名身份。Android 同包名同签名覆盖安装保留数据；实际安装前不写“升级数据保持通过”。
4. 交付 APK 及大体积证据放 `E:/AII-3D/hiplab-releases/<task>/`；凭据、私有构建参数、用户数据备份和日志留 Git 忽略位置，不写入文档或提交。文档仅记录 AI 配置是否具备和验证结果。
5. 有构建/安装/发布就追加版本台账；检查入验证台账，当前事实入当前状态，待验事项入开发事项，关键成果入日志。随后同步两处 README 摘要和本页快照，保留历史日期和证据边界。
6. 检查差异与本地链接，明确路径暂存、提交；在既有授权下普通推送 main 并回读远端 SHA。不 force push，不因文档对齐执行 tag、商店上传或发布配置变更。本轮没有商店发布授权。
